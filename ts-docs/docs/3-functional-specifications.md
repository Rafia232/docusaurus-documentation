# 3. Functional & Non-Functional Specifications

This section defines the functional requirements for the two portals, the system's Non-Functional Requirements (NFRs), and the core validation and business rules.

---

## 3.1 Module 1: Facility User Self-Service Portal

This portal is a dedicated user environment designed for health facility staff (e.g., Dr. Mary) to report issues and track resolutions.

### 3.1.1 My Tickets Page & Dashboard
- **Summary Cards**: Displays metrics for *Total Tickets*, *Open Tickets*, *In Progress Tickets*, and *Closed Tickets* scoped only to the logged-in user's facility.
- **Search & Filtering**: Search by Ticket Title or Ticket ID (`#000001`). Filter by Status and Priority.
- **Ticket Cards**: Renders search results displaying: Title, ID, Description snippet, Created Date, Message Count, Category badge, Status indicator, Priority indicator, and an Attachment Indicator.

### 3.1.2 Open New Ticket Page
- **Input Fields**: Title, Detailed Description, Category.
- **Auto-filled Contact Info**: Displays the requestor's Name, Email, Phone, and originating Facility.
- **Attachments Component**: Drag-and-drop selector accepting `PDF`, `DOC`, `DOCX`, `TXT`, `JPG`, and `PNG` up to **5 MB**.
- **Device Linking**: Dropdown allowing selection from registered devices at the user's facility.

### 3.1.3 Ticket Details Page
- **Information Panel**: Shows Created Date, Due Date, Priority, and Status.
- **Contact Details**: Displays Submitter Name, Email, Phone, and Facility Name.
- **Unified Conversation Workspace**: Thread showing Client Messages, Staff Replies, and Resolution Updates.
- **Reply Editor**: Rich text input with file attachment upload.

---

## 3.2 Module 2: Service Desk Administration Portal

Designed for administrative and technical support operators (Adam, Joseph, and John).

### 3.2.1 Tickets Management Module
- **Dashboard Metrics**: Global indicators of total, open, in progress, and closed tickets.
- **Ticket Sources**: Distinguishes between tickets originating from the *Public Portal*, *Direct Email*, *WhatsApp*, and *Internal Forms*.
- **Workflow Actions**: Creates, edits, assigns, reassigns, and transfers tickets.
- **Internal Collaboration**: Enables posting private Internal Notes visible only to Admins and Experts.

### 3.2.2 Teams & Categories Configuration Modules
- **Teams**: Create support teams, assign leaders (Team Leads), and link experts.
- **Categories**: Create, edit, and delete category taxonomies (e.g. *Software Issue*, *Network Issue*).
- **Category Team Mapping**: Matrix routing categories to specific teams.

---

## 3.3 Non-Functional Requirements (NFRs)

- **Security**: HTTPS TLS 1.3 encryption. API calls validated using bearer JWT tokens. Databases use bcrypt hashing for credentials.
- **Performance**: React SPA page rendering under **2.0 seconds**. REST API latencies under **400ms** (excluding file uploads).
- **Scalability**: Microservices (User, Ticket, Device) run stateless inside Kubernetes pods. Kafka handles asynchronous communications.
- **Reliability & Availability**: Target **99.9%** system availability. PostgreSQL replication provides failover with Recovery Time Objective (RTO) under 15 minutes and Recovery Point Objective (RPO) under 5 minutes.
- **Auditability**: Table triggers block updates or deletes on the `activity_logs` table.

---

## 3.4 Business Rules

- **Ticket ID Format**: Sequential 6-digit integer prefixed by `#` (e.g., `#000001`, `#000002`). Generated by database identity counters.
- **Email Ingestion**: Parses emails sent to `[EMAIL_ADDRESS]`, extracting sender info and creating a ticket with source `Email`.
- **Assignment Scope**: A ticket can only be assigned to an Expert who is an active member of the team currently holding the ticket.
- **Reopen Grace Period**: Reopening a closed ticket changes status to `Open` only if requested within **7 days** of closure.
- **Device Association**: A device can only be linked to a ticket if its registered facility code matches the ticket's originating facility.
- **Internal Notes**: Internal notes are private and must never trigger client-facing notifications or display on the self-service portal.

## 3.5 Validation Rules

| Field Name | Data Type | Constraint | Error Message (if validation fails) |
|:---|:---|:---|:---|
| **Title** | String | Required, Min 10 / Max 150 chars | "Title must be between 10 and 150 characters." |
| **Description** | Text | Required, Min 30 / Max 2000 chars | "Description must be between 30 and 2000 characters." |
| **Category** | Selection | Required | "Please select a valid ticket category." |
| **Attachment Size** | Binary | Max 5,242,880 bytes (5 MB) | "File exceeds maximum size of 5 MB." |
| **Attachment Type** | File MIME | Must match: PDF, DOC, DOCX, TXT, JPG, PNG | "Unsupported file format." |
| **Device Code** | String | Unique, matches format `DEV-XXXXXX` | "Invalid device code format." |
| **Resolution Text** | Text | Required for Close status, min 20 chars | "Resolution details must be at least 20 characters." |
